# Пайплайн кандидатов по вакансии — дизайн-документ

**Дата:** 2026-05-26
**Статус:** на ревью

## Цель

Дать возможность вести кандидата по фиксированным этапам найма в рамках конкретной вакансии: перемещать его между этапами, видеть полную историю перемещений, смотреть на странице вакансии «доску» (kanban) с дизайнерами по этапам, а на карточке кандидата — список вакансий, по которым он идёт, с текущим этапом и историей.

## Контекст и проблема

Сейчас связь «кандидат ↔ вакансия» в системе размазана по трём сущностям:

- `MatchResult` / `DetailedScore` — результат AI-скоринга кандидата под вакансию;
- `ScreeningResult.poolStatus` — ручной review дизайн-лидом результата AI-скрининга (NEW / REVIEWED / APPROVED / REJECTED_MANUAL / MAYBE);
- `ShortlistEntry` — «избранное»: тумблер на карточке матчинга + счётчик в шапке вакансии.

Ни одна из них не отражает, **на каком этапе найма** находится кандидат по вакансии и **как он туда попал**. Нет истории. Шорт-лист дублирует идею «кандидат выбран под вакансию», но без этапов.

## Решение (обзор)

Вводим единый пайплайн: запись «кандидат × вакансия» с текущим этапом из фиксированного глобального списка и полной историей переходов.

- **`ShortlistEntry` переосмысляется в `Pipeline`** — та же связь candidate×vacancy (unique), но поле `status: ShortlistStatus` заменяется на `stage: PipelineStage`. Шорт-лист как отдельная концепция удаляется: «в работе» (этапы ≥ «Одобрен ДЛ») по смыслу и есть бывший шорт-лист.
- **`StageTransition`** — новая модель истории: каждое перемещение фиксирует `fromStage`, `toStage`, актора (свободный текст, т.к. авторизации нет), необязательную заметку, время.
- **`ScreeningResult.poolStatus`** остаётся на уровне данных (AI-скрининг PASS/REJECT и его хранение не трогаем), но его ручной review-UI вытесняется пайплайном. В этой итерации pool-review UI не удаляем, только перестаём развивать; полное удаление — отдельная задача.

### Список этапов (фиксированный, единый для всех вакансий)

12 этапов. Первые два скрыты на доске вакансии (там слишком много людей — вся база и все новые). Триаж ранних этапов делается из карточки кандидата.

| # | enum | Подпись | Виден на доске | Комментарий |
|---|------|---------|----------------|-------------|
| 1 | `BASE` | База | нет | Кандидат отложен по этой вакансии (не в активной работе, но не отказ) |
| 2 | `NEW` | Новый | нет | Прошёл AI-скрининг по вакансии, ждёт триажа ДЛ |
| 3 | `NEEDS_CLARIFICATION` | Нужны уточнения | да | ДЛ пометил, что надо доуточнить (необязательный) |
| 4 | `CLARIFYING` | На уточнении | да | Связываемся, уточняем интерес (необязательный) |
| 5 | `DL_APPROVED` | Одобрен ДЛ | да | ДЛ одобрил кандидата под эту вакансию |
| 6 | `IN_CLIENT_SELECTION` | В подборке для клиента | да | Положили в таблицу клиенту на оценку |
| 7 | `REHEARSAL` | Репетиция | да | Внутренняя подготовка кандидата к созвону |
| 8 | `CLIENT_INTERVIEW` | Интервью с клиентом | да | Созвон с клиентом |
| 9 | `TEST_TASK` | Тестовое задание | да | Выдано / ждём оценку клиента |
| 10 | `OFFER` | Оффер | да | Оффер по вакансии |
| 11 | `REJECTED` | Отказ | да | Отказ по вакансии (терминальный) |
| 12 | `HIRED` | Нанят | да | Нанят (терминальный) |

`enum PipelineStage` объявляется в этом порядке — порядок в БД задаёт порядок колонок на доске.

Доска показывает этапы 3–12 (10 колонок). «База» и «Новый» — только в карточке кандидата.

**Почему 1–2 скрыты:** записи на этапах `BASE`/`NEW` создаются массово (см. «Жизненный цикл» — автосоздание при прохождении AI-скрининга). В этих этапах по вакансии могут быть сотни кандидатов, поэтому на доске их нет — доска показывает только тех, кого ДЛ активно ведёт (этапы 3+). Триаж «Новый → этап 3+» (или «Новый → Отложить в Базу») делается из карточки кандидата либо из списка матчинга на странице вакансии.

## Модель данных

### `Pipeline` (бывший `ShortlistEntry`)

```prisma
model Pipeline {
  id          String    @id @default(cuid())
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  candidateId String
  candidate   Candidate @relation(fields: [candidateId], references: [id], onDelete: Cascade)
  vacancyId   String
  vacancy     Vacancy   @relation(fields: [vacancyId], references: [id], onDelete: Cascade)

  stage       PipelineStage @default(NEW)
  notes       String?

  transitions StageTransition[]

  @@unique([candidateId, vacancyId])
}
```

### `StageTransition` (новая)

```prisma
model StageTransition {
  id         String        @id @default(cuid())
  createdAt  DateTime      @default(now())

  pipelineId String
  pipeline   Pipeline      @relation(fields: [pipelineId], references: [id], onDelete: Cascade)

  fromStage  PipelineStage?   // null для первого попадания в пайплайн
  toStage    PipelineStage
  actor      String           // кто переместил — свободный текст ("Слава", "Наташа", "Система")
  note       String?
}
```

### `enum PipelineStage`

```prisma
enum PipelineStage {
  BASE
  NEW
  NEEDS_CLARIFICATION
  CLARIFYING
  DL_APPROVED
  IN_CLIENT_SELECTION
  REHEARSAL
  CLIENT_INTERVIEW
  TEST_TASK
  OFFER
  REJECTED
  HIRED
}
```

### Обновляются связи

В `Candidate` и `Vacancy` обратные связи переименовываются:

```prisma
// Candidate
pipelines  Pipeline[]   // было: shortlistEntries ShortlistEntry[]

// Vacancy
pipeline   Pipeline[]   // было: shortlist ShortlistEntry[]
```

### Удаляется

- `enum ShortlistStatus` — больше не используется.

### Миграция данных

Существующие `ShortlistEntry` (если есть) переносятся в `Pipeline` с маппингом `status → stage`:

| ShortlistStatus | PipelineStage |
|-----------------|---------------|
| PENDING | NEW |
| CONTACTED | CLARIFYING |
| INTERESTED | DL_APPROVED |
| NOT_INTERESTED | REJECTED |
| INTERVIEWING | CLIENT_INTERVIEW |
| OFFERED | OFFER |
| HIRED | HIRED |
| REJECTED | REJECTED |

Поле `addedBy` шорт-листа отбрасывается (нет прямого аналога — историю начинаем с одной записи `StageTransition { fromStage: null, toStage: <mapped>, actor: addedBy }`). Это инструмент на раннем этапе с минимальными реальными данными — маппинг достаточен, ручная выверка не требуется.

## Жизненный цикл и инварианты

### Единая точка создания

Все способы создания записи проходят через один серверный хелпер `ensurePipeline(candidateId, vacancyId, actor, stage = NEW)`:

- Если запись `Pipeline` для пары уже есть — возвращает её без изменений (идемпотентно, новых переходов не пишет).
- Если записи нет — создаёт `Pipeline { stage }` и одновременно первую `StageTransition { fromStage: null, toStage: stage, actor }`.

Этот хелпер вызывается из:

1. **AI-скрининга** (`ai-screener`): для каждого кандидата с `decision = PASS` вызывается `ensurePipeline(candidateId, vacancyId, "Система", NEW)`. Так этапы `NEW`/`BASE` массово наполняются — это и есть причина, по которой они скрыты с доски.
2. **Ручного добавления** из UI (`POST /api/vacancies/[id]/pipeline`).

Перемещение (`move`) **не создаёт** запись — оно требует существующую (создание и перемещение разведены, чтобы история писалась единообразно).

### Перемещение

- Любой переход (через меню) меняет `Pipeline.stage` и создаёт `StageTransition { fromStage: прежний, toStage: новый, actor, note? }`. Транзакция атомарна.
- Перемещение возможно на любой этап (вперёд/назад), включая `BASE` и терминальные — без жёстких правил переходов: дизайн-лид сам решает.
- **Терминальные этапы** (`REJECTED`, `HIRED`) — обычные этапы; из них тоже можно вернуть кандидата (новый переход). Никаких автодействий с `Candidate.status` / `Vacancy.status` в этой итерации.

### Прочее

- **Актор** берётся из свободного поля ввода (как `reviewedBy` сейчас). Дефолт — последнее введённое значение в localStorage, иначе «Система».
- **Уникальность.** Один кандидат — максимум одна запись Pipeline на вакансию (`@@unique`). По разным вакансиям — независимые записи.
- **«Нет записи» ≠ `BASE`.** Отсутствие строки Pipeline означает «кандидата не скринили по этой вакансии / отсеян на скрининге (REJECT)». `BASE` — это явно отложенный кандидат (есть строка, есть история). Это разные состояния.

## API

Все эндпоинты — Next.js route handlers под `src/app/api`.

### Доска вакансии

`GET /api/vacancies/[id]/pipeline`
Возвращает все записи Pipeline по вакансии, сгруппированные/отсортированные по этапу, с минимальными данными кандидата (`id, name, role, grade`) и его overall score из `DetailedScore`/`MatchResult` (для отображения % на карточке) и `daysInStage` (вычисляется из последней `StageTransition`). Доска на клиенте сама прячет этапы `BASE`/`NEW`.

### Перемещение

`POST /api/vacancies/[id]/pipeline/[candidateId]/move`
Тело: `{ toStage: PipelineStage, actor: string, note?: string }`.
Транзакция: обновляет `Pipeline.stage`, создаёт `StageTransition`. Возвращает обновлённую запись. **Требует существующую запись** — если `Pipeline` для пары нет, возвращает `404` (создание — отдельный эндпоинт ниже). Так путь создания единственный.

### Добавление в пайплайн

`POST /api/vacancies/[id]/pipeline`
Тело: `{ candidateId, actor, stage? }` (по умолчанию `NEW`). Делегирует в `ensurePipeline` — идемпотентно: если запись есть, возвращает её без нового перехода; если нет — создаёт + первую `StageTransition`.

### Карточка кандидата

`GET /api/candidates/[id]/pipelines`
Возвращает все Pipeline кандидата с данными вакансии (`id, title, clientName, grade`), текущим этапом и полной историей `transitions` (отсортирована по `createdAt` desc).

### Замена шорт-листа

Маршрут `POST/DELETE /api/vacancies/[id]/shortlist` удаляется. Точки вызова в UI заменяются на pipeline-эндпоинты.

## UI

### Страница вакансии — доска (kanban)

Новый раздел на `src/app/vacancies/[id]/page.tsx`. Поскольку таб-системы сейчас нет, доска размещается как отдельный блок «Воронка» под брифом вакансии (или заменяет нынешний inline-список матчинга — уточняется при планировании; по умолчанию — добавляем блок «Воронка», а матчинг остаётся источником, откуда добавляют в воронку).

- Горизонтально скроллящийся ряд из 10 колонок (этапы 3–12).
- Каждая колонка: заголовок (цветная точка + подпись + счётчик), список карточек кандидатов.
- Карточка: имя, роль, % матча (цвет по диапазону), дни в этапе. Клик → меню перемещения.
- Меню перемещения: список всех этапов (с цветными точками) + «Открыть карточку». Выбор этапа → запрос актора (инлайн, с дефолтом из localStorage) → `move`.
- Терминальные этапы (Отказ) — приглушённые карточки.

### Карточка кандидата — «Вакансии в работе»

Новый раздел на `src/app/candidates/[id]/page.tsx` (рядом с существующим блоком «Вакансии», который показывает матчинг — они разные: матчинг = «куда подходит по AI», пайплайн = «куда реально двигается»).

- Заголовок секции + кнопка «+ Добавить в вакансию» (выбор вакансии из списка открытых → создаёт Pipeline на этапе NEW).
- Для каждой вакансии в работе: название + клиент + грейд, бейдж текущего этапа (цвет по этапу), таймлайн истории (этап / актор / «N дней назад»), кнопка «Переместить этап».
- Здесь доступны **все** этапы, включая `BASE`/`NEW` (ранний триаж делается отсюда).

### Константы

В `src/lib/constants.ts` добавляются:

- `PIPELINE_STAGE_LABELS: Record<PipelineStage, string>` — русские подписи из таблицы выше.
- `PIPELINE_STAGE_ORDER: PipelineStage[]` — канонический порядок.
- `PIPELINE_STAGE_COLORS: Record<PipelineStage, string>` — цвет точки/бейджа.
- `BOARD_VISIBLE_STAGES: PipelineStage[]` — этапы 3–12 для доски.

## Чистая (тестируемая) логика

Выделяется в чистые функции с unit-тестами (Vitest, как в проекте уже принято):

- `daysInStage(lastTransitionAt: Date, now: Date): number` — целые дни, с округлением вниз, 0 для сегодня.
- `groupPipelineByStage(entries): Record<PipelineStage, Entry[]>` — группировка для доски, сохраняет порядок этапов.
- `mapShortlistStatusToStage(status): PipelineStage` — маппинг для миграции (чистая функция, покрыта тестами по таблице маппинга).

## Что НЕ входит (YAGNI)

- Drag-and-drop перемещение (решено: только через меню).
- Кастомизация этапов под вакансию (этапы фиксированы глобально).
- Правила допустимых переходов между этапами / валидация порядка.
- Автоизменение `Candidate.status` / `Vacancy.status` по этапу.
- Удаление pool-review UI (`poolStatus`) — отдельная задача.
- Уведомления, напоминания, SLA по времени в этапе.

## Открытые вопросы для ревью

1. **Автонаполнение `NEW` при скрининге.** Спека предполагает, что каждый кандидат с `PASS` по вакансии автоматически получает запись Pipeline на этапе `NEW`. Это объясняет «много людей» на скрытых этапах. Подтвердить, что это желаемое поведение (альтернатива — добавлять в пайплайн только вручную).
2. Блок «Воронка» на странице вакансии — добавляем рядом с матчингом или матчинг сворачивается внутрь воронки? (по умолчанию — добавляем рядом).
3. Нужен ли быстрый фильтр на доске (скрыть Отказ/Нанят)? (по умолчанию — нет в этой итерации).

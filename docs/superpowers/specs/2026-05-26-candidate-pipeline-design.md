# Пайплайн кандидатов по вакансии — дизайн-документ

**Дата:** 2026-05-26
**Статус:** на ревью

## Цель

Дать возможность вести кандидата по фиксированным этапам найма в рамках конкретной вакансии: перемещать его между этапами, видеть полную историю перемещений, смотреть на странице вакансии «доску» (kanban) с дизайнерами по этапам, а на карточке кандидата — список вакансий, по которым он идёт, с текущим этапом и историей. Отдельно — глобальный триаж кандидата (где он во всей базе) на его карточке.

## Контекст и проблема

Сейчас связь «кандидат ↔ вакансия» размазана по трём сущностям:

- `MatchResult` / `DetailedScore` — результат AI-скоринга кандидата под вакансию;
- `ScreeningResult.poolStatus` — ручной review дизайн-лидом результата AI-скрининга (NEW / REVIEWED / APPROVED / REJECTED_MANUAL / MAYBE);
- `ShortlistEntry` — «избранное»: тумблер на карточке матчинга + счётчик в шапке вакансии.

Ни одна не отражает, **на каком этапе найма** находится кандидат по вакансии и **как он туда попал**. Нет истории. Шорт-лист дублирует идею «кандидат выбран под вакансию», но без этапов.

## Решение (обзор)

Модель делится на **два уровня**:

1. **Глобальный триаж кандидата** — поле на `Candidate`. Где кандидат во всей базе: только загружен, требует уточнений, на уточнении, отложен в базу. Это НЕ привязано ни к какой вакансии. Управляется из карточки кандидата.
2. **Пайплайн вакансии** — запись «кандидат × вакансия» (`Pipeline`, бывший `ShortlistEntry`) с этапом и полной историей переходов (`StageTransition`). **Запись создаётся только когда дизайн-лид одобряет кандидата под конкретную вакансию** — раньше этого момента кандидат к вакансии не привязан.

Шорт-лист как отдельная концепция удаляется: «одобрен под вакансию и идёт по ней» (Pipeline) по смыслу и есть бывший шорт-лист.

`ScreeningResult.poolStatus` остаётся на уровне данных (хранение AI-скрининга PASS/REJECT не трогаем), но его ручной review-UI вытесняется этой моделью. Полное удаление pool-review UI — отдельная задача.

### Уровень 1: глобальный триаж кандидата

Фиксированный список из 4 состояний (`enum TriageStatus`, поле `Candidate.triageStatus`):

| enum | Подпись | Комментарий |
|------|---------|-------------|
| `NEW` | Новый | Загружен в базу, AI оценил, ждёт триажа ДЛ (дефолт) |
| `NEEDS_CLARIFICATION` | Нужны уточнения | ДЛ пометил: надо что-то доуточнить у кандидата |
| `CLARIFYING` | На уточнении | Связываемся, идёт уточнение |
| `BASE` | База | Просмотрен и отложен в общий пул (на будущее) |

Это состояние живёт на кандидате независимо от вакансий. Кандидат может одновременно быть в «Базе» глобально и идти по двум вакансиям в пайплайнах.

### Уровень 2: пайплайн вакансии

Фиксированный список из 8 этапов (`enum PipelineStage`, поле `Pipeline.stage`). Все 8 показываются на доске вакансии — скрывать нечего, т.к. массовые состояния (вся база) живут на уровне кандидата.

| # | enum | Подпись | Комментарий |
|---|------|---------|-------------|
| 1 | `DL_APPROVED` | Одобрен ДЛ | ДЛ одобрил кандидата под эту вакансию — точка входа в пайплайн |
| 2 | `IN_CLIENT_SELECTION` | В подборке для клиента | Положили в таблицу клиенту на оценку |
| 3 | `REHEARSAL` | Репетиция | Внутренняя подготовка кандидата к созвону |
| 4 | `CLIENT_INTERVIEW` | Интервью с клиентом | Созвон с клиентом |
| 5 | `TEST_TASK` | Тестовое задание | Выдано / ждём оценку клиента |
| 6 | `OFFER` | Оффер | Оффер по вакансии |
| 7 | `REJECTED` | Отказ | Отказ по вакансии (терминальный) |
| 8 | `HIRED` | Нанят | Нанят (терминальный) |

`enum PipelineStage` объявляется в этом порядке — он задаёт порядок колонок на доске.

## Модель данных

### `Candidate` — новое поле триажа

```prisma
// добавляется в model Candidate
triageStatus     TriageStatus  @default(NEW)
triageUpdatedAt  DateTime?     // когда последний раз меняли триаж
triageUpdatedBy  String?       // кто (свободный текст)
```

Существующий `Candidate.status: CandidateStatus` (NEW / PARSED / PORTFOLIO_ANALYZED / ACTIVE / IN_PROCESS / ARCHIVED) — это **ось обработки** (парсинг/анализ), её не трогаем. `triageStatus` — отдельная ось ручного триажа дизайн-лидом.

### `Pipeline` (бывший `ShortlistEntry`)

```prisma
model Pipeline {
  id          String    @id @default(cuid())
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  candidateId String
  candidate   Candidate @relation(fields: [candidateId], references: [id], onDelete: Cascade)
  vacancyId   String
  vacancy     Vacancy   @relation(fields: [vacancyId], references: [id], onDelete: Cascade)

  stage       PipelineStage @default(DL_APPROVED)
  notes       String?

  transitions StageTransition[]

  @@unique([candidateId, vacancyId])
}
```

### `StageTransition` (новая) — история пайплайна вакансии

```prisma
model StageTransition {
  id         String         @id @default(cuid())
  createdAt  DateTime       @default(now())

  pipelineId String
  pipeline   Pipeline       @relation(fields: [pipelineId], references: [id], onDelete: Cascade)

  fromStage  PipelineStage?    // null для первого попадания в пайплайн (= одобрения)
  toStage    PipelineStage
  actor      String            // кто переместил — свободный текст ("Слава", "Наташа")
  note       String?

  @@index([pipelineId])         // история по пайплайну
}
```

История ведётся только для пайплайна вакансии (значимая воронка). Для глобального триажа хранится лишь текущее состояние + кто/когда менял (`triageUpdatedAt/By`) — без полной истории (см. YAGNI).

### Enums

```prisma
enum TriageStatus {
  NEW
  NEEDS_CLARIFICATION
  CLARIFYING
  BASE
}

enum PipelineStage {
  DL_APPROVED
  IN_CLIENT_SELECTION
  REHEARSAL
  CLIENT_INTERVIEW
  TEST_TASK
  OFFER
  REJECTED
  HIRED
}
```

### Обновляются связи

```prisma
// Candidate
pipelines  Pipeline[]   // было: shortlistEntries ShortlistEntry[]

// Vacancy
pipelines  Pipeline[]   // было: shortlist ShortlistEntry[]
```

### Удаляется

- `enum ShortlistStatus` — больше не используется.

### Миграция данных

1. Всем существующим `Candidate` проставляется `triageStatus = NEW` (дефолт).
2. Существующие `ShortlistEntry` переносятся в `Pipeline` с маппингом `status → stage`. Поскольку шорт-лист = «кандидат уже выбран под вакансию», все статусы мапятся на этап `DL_APPROVED` и выше:

| ShortlistStatus | PipelineStage |
|-----------------|---------------|
| PENDING | DL_APPROVED |
| CONTACTED | DL_APPROVED |
| INTERESTED | DL_APPROVED |
| NOT_INTERESTED | REJECTED |
| INTERVIEWING | CLIENT_INTERVIEW |
| OFFERED | OFFER |
| HIRED | HIRED |
| REJECTED | REJECTED |

Для каждой перенесённой записи создаётся одна `StageTransition { fromStage: null, toStage: <mapped>, actor: <старое addedBy или "Система"> }`. Это инструмент на раннем этапе с минимальными реальными данными — маппинг достаточен, ручная выверка не требуется.

**Порядок миграции важен:** данные из `ShortlistEntry.status` нужно прочитать и перенести в `Pipeline`/`StageTransition` **до** удаления колонки/enum. То есть либо data-миграция выполняется внутри той же миграции до drop, либо разбивается на два шага (сначала перенос, потом удаление `ShortlistStatus`). Это отмечается в плане реализации.

## Жизненный цикл и инварианты

### Глобальный триаж (уровень 1)

- Меняется из карточки кандидата: `NEW → NEEDS_CLARIFICATION → CLARIFYING → BASE` (любой переход, без жёстких правил). При изменении проставляются `triageUpdatedAt = now`, `triageUpdatedBy = actor`.
- Никак не привязан к вакансиям и не создаёт записей `Pipeline`.

### Вход в пайплайн вакансии = одобрение ДЛ (уровень 2)

- Запись `Pipeline` для пары candidate×vacancy создаётся **только** действием «Одобрить под вакансию». Точки входа в UI:
  1. Список матчинга / пула на странице вакансии — кнопка «Одобрить» у кандидата.
  2. Карточка кандидата — «+ Добавить в вакансию» (выбор вакансии).
- Оба пути вызывают один серверный хелпер `approveToVacancy(candidateId, vacancyId, actor)`:
  - Если запись уже есть — возвращает её без изменений (идемпотентно, нового перехода не пишет).
  - Если нет — создаёт `Pipeline { stage: DL_APPROVED }` + первую `StageTransition { fromStage: null, toStage: DL_APPROVED, actor }`.
- Автосоздание из AI-скрининга **не делается** — на вакансию кандидат попадает только после явного одобрения ДЛ.

### Перемещение по этапам

- Любой переход (через меню) меняет `Pipeline.stage` и создаёт `StageTransition { fromStage: прежний, toStage: новый, actor, note? }`. Транзакция атомарна.
- Перемещение возможно на любой этап (вперёд/назад), включая терминальные — без жёстких правил: дизайн-лид сам решает.
- **Терминальные этапы** (`REJECTED`, `HIRED`) — обычные этапы; из них тоже можно вернуть кандидата (новый переход). Никаких автодействий с `Candidate.status` / `triageStatus` / `Vacancy.status` в этой итерации.

### Прочее

- **Актор** берётся из свободного поля ввода (как `reviewedBy` сейчас). Дефолт — последнее введённое значение в localStorage, иначе «Система».
- **Уникальность.** Один кандидат — максимум одна запись Pipeline на вакансию (`@@unique`). По разным вакансиям — независимые записи.
- **«Нет записи Pipeline»** означает «кандидат ещё не одобрен под эту вакансию». Это не отдельный этап.

## API

Все эндпоинты — Next.js route handlers под `src/app/api`.

### Глобальный триаж

`PATCH /api/candidates/[id]/triage`
Тело: `{ triageStatus: TriageStatus, actor: string }`. Обновляет `triageStatus`, `triageUpdatedAt`, `triageUpdatedBy`. Возвращает кандидата.

### Доска вакансии

`GET /api/vacancies/[id]/pipeline`
Возвращает все записи Pipeline по вакансии с минимальными данными кандидата (`id, name, role, grade`), его overall score (для % на карточке; берём `DetailedScore.overallScore`, при отсутствии — fallback на `MatchResult.overallScore`, иначе null) и `daysInStage` (из последней `StageTransition`). Клиент группирует по этапу.

### Одобрение под вакансию (создание записи)

`POST /api/vacancies/[id]/pipeline`
Тело: `{ candidateId, actor }`. Делегирует в `approveToVacancy` — идемпотентно создаёт запись на `DL_APPROVED` + первую `StageTransition`.

### Перемещение

`POST /api/vacancies/[id]/pipeline/[candidateId]/move`
Тело: `{ toStage: PipelineStage, actor: string, note?: string }`.
Транзакция: обновляет `Pipeline.stage`, создаёт `StageTransition`. **Требует существующую запись** — если её нет, `404` (создание — только через `POST /pipeline`). Так путь создания единственный.

### Карточка кандидата

`GET /api/candidates/[id]/pipelines`
Возвращает все Pipeline кандидата с данными вакансии (`id, title, clientName, grade`), текущим этапом и полной историей `transitions` (по `createdAt` desc).

### Замена шорт-листа

Маршрут `POST/DELETE /api/vacancies/[id]/shortlist` удаляется; вызовы в UI заменяются на pipeline-эндпоинты.

## UI

### Страница вакансии — доска (kanban)

Новый блок «Воронка» на `src/app/vacancies/[id]/page.tsx` (таб-системы сейчас нет — добавляется как раздел под брифом; существующий список матчинга остаётся источником, откуда «Одобряют» в воронку).

- Горизонтально скроллящийся ряд из **8 колонок** (этапы `DL_APPROVED` → `HIRED`).
- Колонка: заголовок (цветная точка + подпись + счётчик), карточки кандидатов.
- Карточка: имя, роль, % матча (цвет по диапазону), дни в этапе. Клик → меню перемещения.
- Меню: список всех 8 этапов (с цветными точками) + «Открыть карточку». Выбор этапа → запрос актора (инлайн, дефолт из localStorage) → `move`.
- Терминальный «Отказ» — приглушённые карточки.
- В списке матчинга у каждого кандидата кнопка «Одобрить» (если ещё нет Pipeline) или бейдж текущего этапа (если уже в воронке).

### Карточка кандидата

Два раздела на `src/app/candidates/[id]/page.tsx`:

**a) Триаж** (компактный блок наверху): текущий `triageStatus` бейджем + дропдаун смены (Новый / Нужны уточнения / На уточнении / База). Смена дёргает `PATCH /triage`.

**b) «Вакансии в работе»**: заголовок + кнопка «+ Добавить в вакансию» (выбор открытой вакансии → `approveToVacancy`). Для каждой вакансии: название + клиент + грейд, бейдж текущего этапа (цвет по этапу), таймлайн истории (этап / актор / «N дней назад»), кнопка «Переместить этап». Существующий блок «Вакансии» (матчинг — «куда подходит по AI») остаётся отдельно: это разные вещи.

### Константы

В `src/lib/constants.ts` добавляются:

- `TRIAGE_STATUS_LABELS: Record<TriageStatus, string>` — подписи триажа.
- `PIPELINE_STAGE_LABELS: Record<PipelineStage, string>` — подписи этапов.
- `PIPELINE_STAGE_ORDER: PipelineStage[]` — канонический порядок (для колонок доски).
- `PIPELINE_STAGE_COLORS` / `TRIAGE_STATUS_COLORS` — цвета точек/бейджей.

## Чистая (тестируемая) логика

Выделяется в чистые функции с unit-тестами (Vitest, как принято в проекте):

- `daysInStage(lastTransitionAt: Date, now: Date): number` — целые дни, округление вниз, 0 для сегодня.
- `groupPipelineByStage(entries): Record<PipelineStage, Entry[]>` — группировка для доски, сохраняет порядок этапов, пустые этапы присутствуют.
- `mapShortlistStatusToStage(status): PipelineStage` — маппинг для миграции; exhaustive switch по всем 8 значениям (type-safe, покрыт тестами).

## Что НЕ входит (YAGNI)

- Drag-and-drop перемещение (решено: только через меню).
- Кастомизация этапов под вакансию (этапы фиксированы глобально).
- Правила допустимых переходов / валидация порядка.
- Автосоздание Pipeline при PASS скрининга (вход — только явное одобрение ДЛ).
- Полная история глобального триажа (храним только текущее состояние + кто/когда).
- Автоизменение `Candidate.status` / `Vacancy.status` по этапу.
- Удаление pool-review UI (`poolStatus`) — отдельная задача.
- Уведомления, напоминания, SLA по времени в этапе.

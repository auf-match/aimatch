# Журнал уточнений к вакансии — дизайн

**Версия:** 2026-05-27
**Статус:** утверждён к реализации

## Цель

После встречи с клиентом дизайн-лид/рекрутёр получает новую информацию о вакансии (новые задачи, red flags, уточнённые референсы, изменения по зарплате и т.п.). Сейчас эти изменения вносятся вручную, и нет следа того, откуда они пришли. Нужно: добавлять запись об уточнении (текстом или аудио со встречи), AI предлагает структурированный дифф к полям вакансии (включая `scoringCriteria`), пользователь поштучно подтверждает изменения. Кандидаты, проскоренные до этих изменений, помечаются как устаревшие — с возможностью пересчёта одной кнопкой.

## Ключевые решения

- **Объём AI-предложений — широкий.** AI работает по всей вакансии: `scoringCriteria`, `keyTasks`, `requiredSkills`, `niceToHaveSkills`, `redFlags`, `salaryRange`, `productDescription` и др. Не ограничено критериями.
- **Форматы ввода:** текст (обязательно) и аудио Zoom (через существующий пайплайн транскрибации). PDF/DOCX — нет, YAGNI.
- **Подтверждение диффа — поштучное.** По каждому предложению чекбокс «применить» + поле редактирования значения. Кнопка «Применить отмеченное».
- **Пересчёт — ручной.** После применения изменений кандидаты помечаются «скор устарел»; общая кнопка «Пересчитать устаревших» прогоняет их через существующий `detailed-scorer`. Никакого авто-пересчёта.
- **Append-only.** Записи `VacancyUpdate` не редактируются и не удаляются — для аудита. Если ошиблись — добавьте новое уточнение.
- **Human-in-the-loop:** AI рекомендует, человек решает. Применять можно частично, значения — править вручную перед применением.

## Архитектура

### Модель данных (Prisma)

Новая модель `VacancyUpdate`:

```
VacancyUpdate {
  id            String
  vacancyId     String  (FK → Vacancy, onDelete: Cascade)
  createdAt     DateTime
  actor         String                 // имя из getPipelineActor()
  kind          VacancyUpdateKind      // TEXT | AUDIO
  rawText       String?                // если TEXT — введённый текст
  audioFileUrl  String?                // если AUDIO — путь к файлу
  transcript    String?                // транскрипт аудио (после обработки)
  status        VacancyUpdateStatus    // PROCESSING | PENDING | APPLIED | DISMISSED | EMPTY
  proposedDiff  Json?                  // структура: [{ field, op, currentValue, proposedValue, reason }]
  appliedDiff   Json?                  // применённое подмножество proposedDiff
  appliedAt     DateTime?
  errorMessage  String?                // если транскрибация/парсинг упали
}

enum VacancyUpdateKind { TEXT AUDIO }
enum VacancyUpdateStatus {
  PROCESSING   // аудио в работе или AI ещё парсит
  PENDING      // дифф готов, ждёт решения пользователя
  APPLIED      // применено (полностью или частично)
  DISMISSED    // отказались от всего
  EMPTY        // AI не нашёл изменений
}
```

На `Vacancy` добавляется одно поле:

```
criteriaUpdatedAt DateTime?   // момент последнего применения диффа
```

Если `criteriaUpdatedAt` null — критерии актуальны для всех. Иначе `DetailedScore.createdAt < criteriaUpdatedAt` ⇒ скор устарел.

### Поток обработки записи

1. Пользователь нажимает «+ Добавить уточнение», заполняет форму (текст и/или аудио), отправляет.
2. Backend создаёт `VacancyUpdate(status=PROCESSING)`.
3. Если есть аудио — транскрибируем через существующий `briefing-audio.ts` + `briefing-transcribe.ts` (Anthropic). Сохраняем `transcript`.
4. Итоговый текст (`rawText` или `transcript` или их склейка) + полная текущая вакансия (все осмысленные поля + `scoringCriteria`) идут в новый промпт `vacancy-update-parse.ts`.
5. Промпт возвращает JSON-массив предложений: `[{ field, op: "set"|"add"|"remove"|"modify", currentValue, proposedValue, reason }]`. Явная инструкция в промпте: **не предлагать изменений, которые уже отражены в текущей вакансии**.
6. Если массив пуст — `status=EMPTY`. Иначе сохраняем `proposedDiff`, `status=PENDING`.
7. Пользователь видит превью, отмечает галочки, при необходимости правит значения в полях, жмёт «Применить отмеченное».
8. Backend применяет отмеченное к вакансии (вакансия → одна транзакция: обновить поля + поставить `criteriaUpdatedAt = now()` если затронут `scoringCriteria` или связанные с матчингом поля + обновить `VacancyUpdate(status=APPLIED, appliedDiff, appliedAt)`).
9. Альтернатива: «Отказаться от всего» → `status=DISMISSED`, вакансия не меняется.

### Какие поля «связаны с матчингом»

Применённое изменение поднимает `criteriaUpdatedAt` (и значит инвалидирует скоры) только если оно затронуло поля, реально используемые скорером: `scoringCriteria`, `keyTasks`, `requiredSkills`, `niceToHaveSkills`, `preferredDomains`, `requiredTools`, `redFlags`, `specialCompetencies`, `needsInternational`. Изменения чисто контекстных полей (`productDescription`, `salaryRange`, `clientNotes`) — не инвалидируют скоры.

### Чистая логика (выносится под Vitest)

- `isStaleScore(scoreCreatedAt, criteriaUpdatedAt)` — простое сравнение.
- `applyDiffSelection(vacancy, proposedDiff, selectedIndexes, edits)` — берёт текущую вакансию, выбранные элементы диффа (с возможными правками значений) и возвращает payload для `prisma.vacancy.update`. Чистая, тестируется юнит-тестами.
- `diffTouchesScoringFields(appliedDiff)` — определяет, нужно ли поднять `criteriaUpdatedAt`.

## UI

### Секция «Уточнения» на странице вакансии

Располагается под основными полями вакансии, до секции «Воронка».

- Заголовок «Уточнения» + кнопка «+ Добавить уточнение».
- Форма открывается inline (или в небольшом модальном окне в стиле проекта): textarea, file picker для аудио (mp3/m4a/wav, проверки как в брифе), кнопка «Отправить».
- После отправки появляется запись в timeline со статусом `PROCESSING` и лоадером. Когда дифф готов — статус меняется на `PENDING`, под записью раскрывается превью.

### Превью диффа

- Сгруппирован по полю вакансии. Для каждого предложения:
  - Чекбокс «применить» (по умолчанию выключен — явный opt-in).
  - Метка поля (`scoringCriteria`, `keyTasks`, …) с переводом на русский (label-словарь).
  - Слева текущее значение, справа предлагаемое (для массивов — diff списков; для `scoringCriteria` — критерий + вес + тип; для строк — текущий vs новый текст).
  - Поле редактирования предлагаемого значения (можно поправить перед применением).
  - Короткое обоснование от AI (1 строка).
- Внизу: «Применить отмеченное (N)» и «Отказаться от всего».

### Timeline записей

- Каждая запись: дата, актор, превью текста (3 строки + «развернуть»), статус-бейдж (`PROCESSING` / `PENDING` / `APPLIED N/M` / `DISMISSED` / `EMPTY`).
- Раскрытие записи показывает полный текст/транскрипт, превью диффа (для `PENDING`) или применённый список (для `APPLIED`).
- Сортировка — новые сверху.

### Список матчинга

- У кандидатов с `DetailedScore.createdAt < criteriaUpdatedAt` отображается бейдж «Скор устарел» рядом с процентом.
- Над списком кнопка «Пересчитать устаревших (N)» (виден только если N > 0). Прогоняет помеченных через существующий `detailed-scorer`.

## Пограничные случаи

- **Аудио длинное / транскрибация медленная.** Запись сразу создаётся, статус `PROCESSING`, в timeline лоадер. Пользователь может закрыть форму и вернуться позже. Когда транскрипт + парсинг готовы — статус меняется.
- **Транскрибация/парсинг упали.** `status` остаётся `PROCESSING`? Нет — добавляется отдельная индикация ошибки через `errorMessage` (status тогда остаётся `PROCESSING` логически некорректен, поэтому: на ошибке записываем `errorMessage` и оставляем запись в `PROCESSING` с пометкой «ошибка», без возможности применить. В UI рядом — кнопка «Повторить», которая запускает обработку заново). Минимально: повтор есть, удаления нет.
- **AI вернул пустой дифф.** Запись сохраняется в timeline (история встречи всё равно полезна), `status=EMPTY`, без превью.
- **Применили часть, остаток хотим позже.** Запись фиксируется как `APPLIED N/M` (где N — применённых, M — изначально предложенных). Остаток в превью не остаётся — повторно не показывается. Захотите доприменить — добавьте новое уточнение с описанием.
- **Передумали по конкретному пункту после применения.** Правите вручную в полях вакансии как обычно. Запись `VacancyUpdate` неизменна (append-only). `criteriaUpdatedAt` от ручной правки не двигается — это правка пользователя, не AI-применение.
- **Удалили вакансию.** `VacancyUpdate` каскадно удаляется вместе с ней (`onDelete: Cascade`).

## API (черновик)

- `POST /api/vacancies/[id]/updates` — multipart-form `{ rawText?, audio? }` → создаёт `VacancyUpdate`, запускает асинхронную обработку, возвращает запись со `status=PROCESSING`.
- `GET /api/vacancies/[id]/updates` — список записей с историей (desc).
- `POST /api/vacancies/[id]/updates/[updateId]/apply` body `{ selections: [{ index, editedValue? }], actor }` — применяет выбранное к вакансии, обновляет запись (`status=APPLIED`, `appliedDiff`, `appliedAt`), и если задеты поля матчинга — поднимает `criteriaUpdatedAt`.
- `POST /api/vacancies/[id]/updates/[updateId]/dismiss` — `status=DISMISSED`.
- `POST /api/vacancies/[id]/updates/[updateId]/retry` — повторная обработка, если упало.
- `POST /api/vacancies/[id]/rescore-stale` body `{ actor }` — пересчитывает скоры всех кандидатов, у которых `DetailedScore.createdAt < criteriaUpdatedAt`, через существующий `detailed-scorer`. Возвращает количество пересчитанных.

## Что не делаем (YAGNI)

- PDF/DOCX как формат ввода — текста и аудио хватит.
- Редактирование/удаление записей `VacancyUpdate` (только append).
- Автоматический пересчёт скоров после каждого применения.
- Откат применённых изменений одной кнопкой (правьте вручную или добавьте новое уточнение).
- Множественный выбор кандидатов для частичного пересчёта — на v1 одна общая кнопка.
- Уведомления / напоминания о новых записях.

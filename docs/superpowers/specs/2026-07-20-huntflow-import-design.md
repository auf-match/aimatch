# Импорт из выгрузки Huntflow — дизайн

**Версия:** 2026-07-20 (v2, после ревью)
**Статус:** утверждён к реализации

## Проблема

Существующий импорт (`docs/superpowers/specs/2026-07-03-behance-import-design.md`) написан под выгрузку профилей Behance. Реальная база агентства — экспорт из Huntflow (ATS), формат совершенно другой.

Загрузка реального файла (`applicants.json`, 94 МБ, 3934 записи) дала:

```
Импортировано 144. Пропущено: уже в базе 2, без имени/ссылки 0. Всего найдено 146.
```

`невалидных 0` при `найдено 146` означает, что узкое место — **извлечение**, а не маппинг: `extractBehanceProfiles` считает профилем только объект, у которого в поле `url` лежит `behance.net`. В Huntflow-записи такого поля нет.

| **С ≥1 ссылкой на портфолио (прототип классификатора)** | **2230** |
| Импортируется сейчас | 144 |

### Где лежат ссылки

Ссылки на портфолио находятся **внутри текста резюме** — `externals[].data.body`. Это единственный источник, который читает дизайн.

**Важно про scope:** инфраструктурный мусор Huntflow/hh.ru (`api.hh.ru`, `hhcdn.ru`, `store.huntflow.ru`, CDN-картинки `mir-s3-cdn-cf.behance.net`) живёт в полях `photos`, `files`, `logs`, `externals[].files` — **в теле резюме его практически нет**. Мы эти поля не читаем, поэтому фильтровать их не нужно.

## Принятые решения

1. **Импортируем только тех, у кого есть ссылка на портфолио** (~2230). Люди без портфолио не заводятся — база остаётся чистой, в выгрузке есть и не-дизайнеры (напр. front-end разработчики).
2. **AI-анализ не меняется** — как и сейчас, скрейпим портфолио-ссылку. Текст резюме из Huntflow для анализа не используем (медиана 240 символов — слишком мало, чтобы окупать усложнение пайплайна). Скрейпер на Playwright уже работает с любой платформой.
3. **Behance-путь сохраняем.** Роут импорта авто-детектит формат.

## Архитектура

### Новый модуль `src/lib/huntflow-import.ts`

Чистая логика без I/O, по образцу `src/lib/behance-import.ts`, покрыта Vitest.

**Экспорт:**
- `isHuntflowExport(json: unknown): boolean` — детектор формата для роута.
- `extractHuntflowApplicants(json: unknown): HuntflowApplicant[]` — берёт `json.items` (массив). Не рекурсивный обход: формат Huntflow плоский и предсказуемый, гадать не нужно.
- `classifyUrls(urls: string[]): { portfolioLinks: string[]; telegram?: string; linkedin?: string }` — ядро фичи, тестируется изолированно.
- `mapApplicantToCandidate(a: HuntflowApplicant): CandidateImportRow | null` — `null`, если нет имени **или** нет ни одной портфолио-ссылки.

### Детектор формата

`json.items` — массив **и** первый элемент содержит `externals` либо `account_source`. Одного `items` мало: гипотетическая другая выгрузка тоже может иметь такое поле. Проверка по маркерному полю Huntflow надёжнее.

### Классификация ссылок

Из склеенных тел резюме (`externals[].data.body` по всем `externals`) регуляркой достаются все URL, затем каждый нормализуется и классифицируется **по хосту** (не подстрокой).

**Почему по хосту, а не подстрокой:** подстрочное совпадение по `hh.ru` поймало бы легитимные домены, а по `behance.net` — CDN-хосты вида `mir-s3-cdn-cf.behance.net`. В теле резюме CDN-хостов практически нет, но реальный случай есть: `spb.hh.ru` (20 человек) — сравнение по хосту отсекает его корректно, а `endsWith("hh.ru")` — нет.

**Allowlist портфолио-хостов** (точное совпадение хоста без `www.`, либо суффикс поддомена):

```
behance.net          dribbble.com         readymag.com        readymag.website
notion.so            *.notion.site        figma.com           designer.ru
dprofile.ru          buildin.ai           setka.ru            lookzine.com
hsedesign.ru         coroflot.com         artstation.com      cargocollective.com
*.myportfolio.com    *.tilda.ws/.cc/.ru   *.super.site        *.framer.website/.ai/.app
*.webflow.io         *.github.io
```

**Особые случаи:**
- `t.me` → `telegramContact`.
- `linkedin.com` и поддомены → `linkedinUrl`.
- Всё остальное игнорируется.

**Сознательно пропускаем `drive.google.com` (285), `disk.yandex.ru` (167), `docs.google.com` (65)** — это крупнейшая не-портфолио категория, и там действительно бывают портфолио-PDF. Но Playwright-скрейпер за ними не пройдёт: авторизация, вьюеры, бинарные файлы. Тащить их — значит гарантированно получить `ANALYSIS_FAILED` и потратить скрейп впустую. Соцсети (`instagram.com` 116, `vk.com` 19) не портфолио.

**Почему allowlist, а не «всё кроме мусора»:** в резюме много ссылок на работодателей и соцсети, перечислить их все в denylist невозможно. Allowlist известных платформ даёт 2230 чистых записей без ложных срабатываний. Редкий кастомный домен пропустим — это дешевле, чем натащить мусор в базу. Список вынесен в константу, расширяется одной строкой.

### Нормализация URL

Порядок: сначала нормализация, **потом** дедуп (иначе `/user` и `/user/` останутся разными записями и дедуп против базы промахнётся).

1. Обрезать хвостовую пунктуацию (`.,;:`), прилипшую при извлечении из текста.
2. Убрать хвостовой `/` — в данных встречаются обе формы (`behance.net/SoniaGrin/` и `behance.net/SoniaGrin`).
3. **Behance:** путь режется до первого сегмента — это профиль. Реальные формы в данных: `/user` (1070), `/gallery/…` (71), `/user/projects` (24), `/user/resume` (8), `/user/moodboards` (5), `/user/info` (3), `/user/appreciated` (1). Вкладки профиля (`projects`, `resume`, `moodboards`, `info`, `appreciated`) отсекаются, остаётся `behance.net/user`. **Исключение:** первый сегмент `gallery` — это отдельный проект, корень профиля из него не вывести, оставляем как есть.
4. **Отбрасываем URL с пустым путём — ТОЛЬКО для хостов из точного списка** (`behance.net`, `dribbble.com`, `dprofile.ru`, `figma.com` и прочие exact-match). У них корень — это главная страница платформы, а не чьё-то портфолио (в данных есть голый `https://www.behance.net`).

   **Для хостов-поддоменов** (`*.tilda.ws`, `*.super.site`, `*.framer.website`, `*.webflow.io`, `*.notion.site`, `*.myportfolio.com`, `*.github.io`) пустой путь **оставляем** — там корень поддомена и ЕСТЬ портфолио: `kuzmiichukt.tilda.ws`, `seterell.webflow.io`, `borodko.super.site`.

   **Это не мелочь:** правило «отбрасывать пустой путь везде» даёт 1875 кандидатов вместо 2230 — молча теряется **355 человек** (16%).

### Ранжирование

Анализ скрейпит `portfolioLinks[0]`, поэтому первой должна стоять самая содержательная ссылка. Каждому allowlist-хосту назначается тир — **непокрытых хостов быть не должно**:

| Тир | Хосты |
|---|---|
| 0 | `behance.net` |
| 1 | `dribbble.com` |
| 2 | **все остальные из allowlist** (readymag, notion, tilda, super.site, framer, webflow, myportfolio, cargocollective, designer.ru, dprofile.ru, buildin.ai, setka.ru, lookzine.com, hsedesign.ru, coroflot, artstation, github.io) |
| 3 | `figma.com` |

Figma — последняя намеренно: это обычно один файл или прототип, а не портфолио целиком. Тир 2 определяется как «в allowlist, но не 0/1/3», поэтому новый хост в списке автоматически получает разумный ранг.

**Сортировка стабильная** — при равном тире порядок сохраняется как в тексте резюме. `portfolioLinks[0]` уходит в скрейп, поэтому разрешение ничьих должно быть детерминированным.

Примерно у 450 человек ссылок несколько — сохраняем все, сортируем по тиру.

### Маппинг полей

| Источник (Huntflow) | Поле кандидата |
|---|---|
| `first_name` + `last_name` (+ `middle_name`) | `name` |
| портфолио-ссылки из `externals[].data.body` | `portfolioLinks` (нормализованы, дедуплицированы, отсортированы) |
| `t.me`-ссылка из тела резюме | `telegramContact` |
| `linkedin.com`-ссылка из тела резюме | `linkedinUrl` |
| `email` (верхний уровень) | `email` |
| `externals[].data.area.name`, иначе `externals[].data.city` | `location` |
| `phone` (верхний уровень) | — **поля `phone` в схеме нет, не пишем** |
| — | `role: "OTHER"`, `grade: "MIDDLE"`, `status: "NEW"`, `source: "huntflow"` |

**Плейсхолдер Huntflow:** у части записей `email` = `office@huntflow.ru` (служебный адрес системы). Любой `@huntflow.ru` отбрасываем. Таких 3 записи из 3934, реальных email — 1241; случай редкий, но фильтр дешёвый.

**Локация:** поля `externals[].data.area.title` **не существует** (проверено). Реальные источники: `externals[].data.area.name` (223 записи, напр. `"Санкт-Петербург"`) и `externals[].data.city` (110, напр. `"Тюмень"`). Берём первое непустое. Покрытие 8.4% (332 из 3934) — остальным локацию проставит AI-анализ (`candidate-analysis.ts` мержит через `data.location ?? candidate.location`, импортированное значение не затирается).

**Не читаем `externals[].data.portfolio` и `externals[].data.site`** (ключ присутствует у 223 записей каждый; оба — **массивы**, не строки):
- `data.portfolio` содержит не портфолио, а вложения-картинки с hh.ru (`hhcdn.ru` — сканы дипломов и сертификатов).
- `data.site` содержит объекты `{url, type}`, напр. `{"url":"https://www.behance.net/SysoletinaE","type":{"id":"personal","name":"Другой сайт"}}` — ссылки там осмысленные, но у всех этих людей те же ссылки уже есть в теле резюме.

Проверено: оба поля дают **0 дополнительных человек** сверх извлечения из `body`. Второй путь извлечения не нужен.

### Правка общего типа `CandidateImportRow`

Текущий тип в `src/lib/behance-import.ts` **не может представить Huntflow-строку**:

```ts
export interface CandidateImportRow {
  name: string; portfolioLinks: string[]; location?: string;
  telegramContact?: string; email?: string;
  role: "OTHER"; grade: "MIDDLE"; status: "NEW"; source: "behance";  // ← литерал
}
```

Две проблемы: `source: "behance"` — литерал, `"huntflow"` не типизируется; поля `linkedinUrl` **нет вообще**, а роут пишет строки в базу как есть (`createMany({ data: toCreate })`) — LinkedIn 521 человека молча потерялся бы.

Тип переезжает в общий модуль (или остаётся в `behance-import.ts` и импортируется — на усмотрение имплементера, главное — один источник истины) со следующими правками:
- `source: ImportSource`, где `ImportSource = "behance" | "huntflow"`;
- добавляется `linkedinUrl?: string`.

Behance-парсер продолжает возвращать `source: "behance"` и просто не заполняет `linkedinUrl`.

### Изменения в существующем коде

1. **`src/app/api/candidates/import-json/route.ts`** — авто-детект: `isHuntflowExport(json)` → Huntflow-парсер, иначе существующий Behance-парсер. Ответ (`{found, imported, skippedExisting, skippedInvalid}`) и логика дедупа не меняются.

   **Сообщение об ошибке зависит от ветки.** Сейчас при нулевом извлечении роут отдаёт 400 «Не найдено профилей Behance в файле». Для Huntflow-ветки нужно своё сообщение (напр. «В выгрузке Huntflow не найдено кандидатов со ссылкой на портфолио») — иначе на валидном Huntflow-файле без подходящих записей пользователь увидит вводящую в заблуждение ошибку про Behance.

2. **`src/app/api/candidates/analyze-batch/route.ts` и `.../status/route.ts`** — фильтр `source: "behance"` (в status он встречается дважды) заменяется на `source: { in: IMPORT_SOURCES }`, где `IMPORT_SOURCES = ["behance", "huntflow"]` — общая константа, чтобы выборка пачки и счётчики не разъехались. Смысл фильтра сохраняется: не захватывать кандидатов, заведённых обычной загрузкой.

3. **`src/app/candidates/upload/import-json-block.tsx`** — строка «Выгрузка профилей Behance» → нейтральная, упоминающая оба формата.

### Что НЕ меняется

- `src/server/services/candidate-analysis.ts` — анализ работает как есть, скрейпер платформо-независим.
- Схема БД — `source` уже строка, новых полей и статусов не нужно.
- Логика Behance-парсера — только тип `CandidateImportRow` расширяется совместимо.
- Эмбеддинги, матчинг, UI порционного анализа.

## Пограничные случаи

- **Нет `externals`** — тела резюме нет, ссылок нет → пропуск (`skippedInvalid`).
- **Несколько `externals`** — тела склеиваются, ссылки собираются из всех.
- **Нет имени** → пропуск.
- **Только `figma.com`** → импортируем, figma станет основной ссылкой (лучше, чем ничего).
- **Человек уже импортирован Behance-путём** — дедуп против базы по основной ссылке отсекает, попадёт в `skippedExisting`. Нормализация хвостового `/` здесь критична.
- **Дубли внутри файла** — схлопываются по основной ссылке, как в Behance-пути.
- **Файл 94 МБ** — текущий роут (`JSON.parse(await file.text())`) уже успешно обработал этот файл целиком, лимиты не трогаем.
- **Битый URL** (не парсится `new URL`) — молча пропускается, не роняет запись.

## Тестирование

Vitest на `src/lib/huntflow-import.ts` — синтетическая Huntflow-запись, покрывает:
- `isHuntflowExport`: `{items:[{externals:…}]}` → true; Behance-выгрузка → false; `{items:[…]}` без маркеров → false;
- извлечение `items`, имя из `first_name`/`last_name`, пропуск без имени;
- allowlist: behance/dribbble/`*.notion.site`/tilda/readymag.website проходят; `spb.hh.ru`, `drive.google.com`, `instagram.com` — нет;
- `t.me` → `telegramContact`, linkedin → `linkedinUrl`, ни то ни другое не попадает в `portfolioLinks`;
- нормализация: `behance.net/user/projects` → `behance.net/user`, хвостовой `/` убирается, `behance.net/gallery/123` не трогается, голый `behance.net` отбрасывается;
- **корень поддомена СОХРАНЯЕТСЯ**: `https://ivan.tilda.ws` и `https://x.framer.website` (пустой путь) должны попасть в `portfolioLinks`. Это страховка от регрессии на 355 человек — без этого теста все остальные проходят и при ошибочной реализации;
- ранжирование (behance раньше figma; хост тира 2 раньше figma) и дедуп после нормализации;
- отбрасывание `@huntflow.ru`;
- `null` без портфолио-ссылок и `null` без имени.

Ручная проверка: пилот на реальном файле — ожидаем ~2230 импортированных (сейчас 144), затем порционный анализ на 10 записях и проверка, что кандидат проходит хард-фильтр матчинга.

## Что не делаем (YAGNI)

- Не используем текст резюме для AI-анализа (решение выше).
- Не добавляем поле `phone` в схему.
- Не читаем `data.portfolio` / `data.site` (+16 человек, не окупается).
- Не тащим Google Drive / Яндекс.Диск (скрейпер их не возьмёт).
- Не обобщаем `isDeadBehancePage` на другие платформы — для не-Behance мёртвой страницы потратим один лишний AI-вызов, чинить преждевременно.
- Не парсим `externals[].data.experience` в `Experience` — опыт добирается AI-анализом.
- Не импортируем людей без портфолио-ссылки.
- Не делаем отдельный роут под Huntflow — авто-детект в существующем.

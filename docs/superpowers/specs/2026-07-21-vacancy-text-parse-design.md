# Заполнение вакансии из вставленного текста — дизайн

**Версия:** 2026-07-21
**Статус:** утверждён к реализации

## Проблема

На странице создания вакансии (`/vacancies/new`) уже есть два способа автозаполнения формы через AI:
- **загрузка PDF/DOCX** → `parse-pdf` → `parseVacancy` → форма;
- **загрузка аудио брифинга** → `parse-audio` → транскрипция → `parseVacancyFromTranscript` → форма с подсветкой «не хватает / низкая уверенность».

Не хватает третьего, самого простого способа: **вставить текст напрямую** (описание вакансии из письма, сообщения в Telegram, заметки) и получить заполненную форму. AI берёт что может, остальное оставляет пустым — пользователь дозаполняет вручную.

## Ключевые наблюдения (инфраструктура уже есть)

- `parseVacancyFromTranscript(text: string)` (в `src/server/services/briefing-audio.ts`) **принимает строку** и возвращает `{ summary, fields }`, где `fields` — это `{ [key]: { value, confidence: "high"|"low"|null } }`. Именно этот формат форма уже умеет раскладывать.
- Логика раскладки в `src/app/vacancies/new/page.tsx` (аудио-хендлер, ~строки 270-330): для каждого поля берёт `value ?? default`, строит карту `fieldHints` со статусами `missing`/`low` — ровно поведение «оставить пустым + подсветить», которое нужно.
- В интро-блоке страницы (~строки 421-560) уже есть UI-карточки загрузки PDF и аудио — текстовый ввод встаёт третьим рядом.

## Принятые решения

1. **Переиспользуем `parseVacancyFromTranscript`** — она уже принимает строку и отдаёт нужный формат. Новый промпт по умолчанию НЕ пишем.
2. **Логику раскладки полей выносим в чистую функцию** — сейчас она зашита в аудио-хендлер; и аудио, и текст будут звать одну функцию (DRY + возможность юнит-теста «пустое остаётся пустым»).
3. **Исходный текст не храним** — в отличие от аудио (где сохраняется транскрипт), вставленный текст нужен только для заполнения формы. `summary` из парсера для текстового пути игнорируем.
4. **Подсветка пустых/неуверенных полей** — работает автоматически, та же, что у аудио.

## Архитектура

### 1. Чистая функция раскладки — `src/app/vacancies/new/parse-fill.ts`

Выносим текущую inline-логику аудио-хендлера в чистую, тестируемую функцию:

```ts
export type FieldStatus = "missing" | "low";

interface ParsedField { value: unknown; confidence: "high" | "low" | null }
type ParsedFields = Record<string, ParsedField | undefined>;

export interface FieldsUpdate {
  data: Partial<VacancyFormData>;
  hints: Map<string, FieldStatus>;
}

/** Раскладывает fields из AI-парсера в частичный апдейт формы + карту подсветок.
 *  Отсутствующее/пустое значение → дефолт формы; статус missing.
 *  confidence "low" → статус low. */
export function buildFieldsUpdate(fields: ParsedFields): FieldsUpdate;
```

`VacancyFormData` и его дефолты уже определены в `page.tsx` — при выносе функции тип импортируется/переносится в общий модуль (имплементер решает по месту, главное — один источник истины, без дублирования списка полей). Список полей и дефолтов — точно тот же, что сейчас в аудио-хендлере (`apply("title", …, "")`, `apply("keyTasks", …, [])` и т.д.), просто перенесённый.

Оба хендлера (аудио и текст) после получения `fields` вызывают `buildFieldsUpdate(fields)` и делают `setData(prev => ({...prev, ...update.data}))` + `setFieldHints(update.hints)`. Дублирование ~60 строк раскладки устраняется.

### 2. Роут — `POST /api/vacancies/parse-text/route.ts`

```ts
{ text: string } → { fields: ParsedFields } | { error }
```

- Валидация: `text` — строка, после `trim()` длиной ≥ ~20 символов (иначе 400 «Текст слишком короткий»). (Порог как у `parse-criteria` — там 10; берём чуть больше, т.к. тут нужен связный текст.)
- Зовёт `parseVacancyFromTranscript(text.trim())`, возвращает `{ fields: parsed.fields }`. `summary` не возвращаем (форме не нужен, текст не храним).
- Ошибка парсинга (AI вернул невалидный JSON / `BriefingAudioError`) → как в `parse-audio`: НЕ 500 наружу, а понятное сообщение. Но, в отличие от аудио, терять нечего (транскрипта нет) — возвращаем `{ error }` со статусом ошибки, клиент покажет «AI не смог структурировать, заполните вручную», форма остаётся пустой и доступной.
- `maxDuration = 60` (один Gemini-вызов, аудио-транскрипции тут нет — 300 не нужно).

### 3. UI — блок ввода текста в интро

Рядом с карточками PDF/аудио добавляется блок:
- `<textarea>` с плейсхолдером-подсказкой (напр. «Вставьте описание вакансии: письмо от клиента, сообщение, заметки…»);
- кнопка «Заполнить из текста» (дизейбл, если текст пустой/короткий или идёт запрос; текст «Обрабатываю…» в процессе);
- сабмит → `POST /api/vacancies/parse-text` с `{ text }` → `buildFieldsUpdate(json.fields)` → `setData` + `setFieldHints`, открыть форму (`setBriefingLoaded(true)` — тот же флаг, что показывает заполненную форму, либо аналог; имплементер сверит, как аудио/PDF раскрывают форму, и повторит);
- ошибка (4xx/5xx или сеть) → inline-сообщение, форма остаётся доступной для ручного заполнения. Введённый текст в textarea не сбрасываем (можно поправить и повторить).

Стиль — как у соседних карточек PDF/аудио (те же контейнеры/отступы/кнопки на этой странице).

## Риск: промпт заточен под транскрипт

`buildBriefingParsePrompt` обрамляет вход как «транскрипт встречи-брифинга» («устная речь», «читай между строк»). На сухом тексте (описание вакансии) это:
- скорее всего сработает — задача структурного извлечения та же;
- но может перебрать с домыслами (confidence, «между строк») или выдать summary в формате пересказа встречи.

**План:** на реализации проверить `parse-text` на 2-3 реальных примерах (письмо/сообщение с описанием вакансии). Если результат адекватный — оставляем переиспользование как есть (summary всё равно игнорируем). Если мажет — минимальная развилка: сделать `buildBriefingParsePrompt(input, source?: "transcript" | "text")`, где `source: "text"` меняет только вводную рамку (2-3 строки: «дан текст с описанием вакансии» вместо «транскрипт встречи», убрать «между строк»), схема ответа и остальной промпт — без изменений. Отдельный сервис/файл не плодим.

## Пограничные случаи

- **Пустой/короткий текст** → 400, кнопка и так задизейблена.
- **AI не смог структурировать** → форма открывается пустой, сообщение «заполните вручную» (как у аудио при `parseError`).
- **Часть полей не извлеклась** → пусто + подсветка «AI не нашёл, заполни вручную» (штатное поведение).
- **Пользователь уже загрузил PDF/аудио, потом вставил текст** → повторный парсинг перезапишет `data`/`hints` (как и повторная загрузка файла сейчас). Приемлемо; отдельной защиты не делаем.
- **Очень длинный текст** → один Gemini-вызов, лимит контекста модели с запасом; спец-обрезку не делаем.

## Тестирование

- **Vitest на `buildFieldsUpdate`** (чистая функция — главная логика «пустое остаётся пустым»):
  - все поля заполнены high → `data` содержит значения, `hints` пуст;
  - поле `null`/пустая строка/пустой массив → в `data` дефолт, в `hints` статус `missing`;
  - `confidence: "low"` при непустом значении → статус `low`;
  - неизвестный ключ в `fields` игнорируется, не роняет функцию.
- **Роут и UI** — без юнит-тестов (тонкая обёртка); проверка вручную: вставить реальный текст → форма заполнилась, пустые поля подсвечены, можно дозаполнить и создать вакансию. Плюс проверка риска промпта (см. выше).

## Что не делаем (YAGNI)

- Не пишем новый промпт заранее (только если проверка покажет, что мажет).
- Не храним вставленный текст в БД.
- Не трогаем PDF/аудио-флоу (кроме выноса общей функции раскладки, которую они теперь тоже зовут).
- Не возвращаем и не показываем `summary` для текстового пути.
- Не добавляем распознавание формата ввода (текст vs что-то ещё) — это просто textarea.

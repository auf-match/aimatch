# Пакетная загрузка кандидатов по портфолио-ссылкам

**Дата:** 2026-05-24
**Статус:** Дизайн утверждён, готов к планированию

## Проблема

Сейчас кандидаты загружаются по одному через `/candidates/upload`. Рекрутеру
часто нужно добавить пачку кандидатов сразу — по списку ссылок на портфолио,
без резюме-файлов. Делать это по одному медленно и утомительно.

Главная сложность: пайплайн обработки одного кандидата тяжёлый (скрейпинг
Playwright + несколько вызовов AI, до 180 секунд) и в двух точках
**останавливается и ждёт решения человека**:

1. **Направление дизайнера** (product / communication) — для неоднозначных
   ролей AI просит выбрать вручную (ответ `409 needsDirection`).
2. **Дубликаты** — если кандидат уже в базе по email/LinkedIn, флоу просит
   подтверждения (ответ `409 duplicate`).

В пакетном режиме нельзя останавливаться на каждом кандидате.

## Решение

### Масштаб и сценарий

Основной сценарий — пачка **5–20 кандидатов** за раз. Это позволяет
обрабатывать ссылки последовательно с живым прогрессом, без фоновой очереди
и персистентного job-state.

### Вход

Массовая загрузка работает по **портфолио-ссылкам без резюме** (режим
«только портфолио» уже поддержан одиночным эндпоинтом).

### Стратегия неоднозначностей: «очередь на решение»

Однозначных кандидатов создаём сразу. Спорных (направление / дубликат)
складываем в очередь на ревью, и рекрутер разбирает их по одному в конце.

### Архитектура: клиентская оркестрация

Новая клиентская страница **`/candidates/upload/bulk`**. Весь оркестратор
живёт в браузере; **бэкенд не меняется**.

Существующий `POST /api/candidates/upload` уже покрывает все нужные случаи:

- принимает только `portfolioLink` (без файла);
- возвращает `201` с карточкой кандидата при успехе;
- возвращает `409` с `needsDirection` (+ `suggestedDirection`, `confidence`,
  `reasoning`, `parsedName`);
- возвращает `409` с `duplicate` (+ `reason`, `existing`, `parsedName`);
- принимает на повторном запросе `direction=product|communication` и
  `forceCreate=true` для разрешения.

Браузер вызывает этот эндпоинт по одной ссылке и трактует ответы. Каждый
запрос укладывается в лимит времени одного HTTP-запроса (180с).

## Поток работы

1. **Ввод — динамический список нумерованных полей.**
   - По умолчанию одно поле для ссылки на портфолио, слева номер `1`.
   - Под полями — кнопка **«+ Добавить ещё кандидата»**; нажатие добавляет
     следующее поле с номером `2`, `3` и т.д.
   - У каждого поля слева — его номер (для ориентации на всём пути от ввода
     до результата).
   - У каждого поля справа — крестик `×` для удаления строки; нумерация ниже
     автоматически пересчитывается. Нельзя удалить последнее оставшееся поле.
   - Кнопка «Обработать» активна, когда есть хотя бы одна непустая валидная
     ссылка. Пустые строки при запуске игнорируются.

2. **Обработка — строго последовательная.**
   - Браузер идёт по непустым ссылкам по одной (один запрос за раз —
     Playwright и AI-квота тяжёлые).
   - Каждая строка — мини-машина состояний:
     `ожидает → обрабатывается → создан / needs-direction / duplicate / ошибка`.
     Статусы `needs-direction` и `duplicate` — это и есть «на ревью»
     (объединяющий ярлык в UI); отдельного состояния `on-review` нет.
   - Сверху живой прогресс «X из N» + кнопка **«Стоп»** (прервать остаток
     очереди; уже запущенный запрос завершается). Непройденные строки
     возвращаются в `ожидает` — обработку можно запустить повторно.

3. **Ревью-очередь.**
   - После прохода строки со статусом «на ревью» разворачиваются с инлайн-
     разрешением:
     - **needsDirection** → переиспользуемый `DirectionPicker`; выбор →
       повторный запрос с `direction=` → строка станет «создан».
     - **duplicate** → блок как `DuplicateWarning`: «Открыть существующего» /
       «Создать всё равно» (`forceCreate=true`) / «Пропустить».
     - **error** → кнопка «Повторить» (повторный запрос по той же ссылке).

4. **Итог.**
   - Шапка-сводка: «Создано N · на ревью M · ошибок K».
   - Ссылка на список кандидатов.

## Компоненты и переиспользование

Сейчас `DirectionPicker` и `DuplicateWarning` зашиты внутри
`src/app/candidates/upload/page.tsx`. Выносим их в `src/components/`:

- `candidate-direction-picker.tsx`
- `candidate-duplicate-warning.tsx`

Так их используют и одиночная, и пакетная загрузка. Одиночная страница
продолжает работать — меняются только импорты. Это целевой рефакторинг под
задачу, без расширения области.

Новые части (всё на странице bulk):

- **`BulkLinkInput`** — список нумерованных полей: добавление/удаление,
  парсинг и валидация ссылок.
- **`BulkProgressList` + `BulkRow`** — отрисовка строк со статусами.
- **`useBulkUpload`** — хук-оркестратор: последовательная очередь, вызовы
  fetch к существующему эндпоинту, разбор `201`/`409`/ошибок, управление
  состоянием строк, прерывание по «Стоп».
- **`parsePortfolioLinks`** — чистый хелпер: чистка пустых, дедуп, валидация
  и нормализация URL. Покрывается юнит-тестом.

## Данные и состояния

Новое состояние в БД не вводится — всё живёт в памяти страницы. Каждая
строка:

```ts
{
  id: string;            // стабильный ключ строки
  url: string;
  status: "idle" | "pending" | "processing" | "created" | "needs-direction" | "duplicate" | "error";
  candidate?: CandidateResult;   // при created
  duplicate?: DuplicateInfo;     // при duplicate
  needsDirection?: NeedsDirectionInfo; // при needs-direction
  error?: string;        // при error
}
```

Карточки создаются обычным `prisma.candidate.create` внутри существующего
эндпоинта — включая эмбеддинг и анализ портфолио (поля `visualStrength`,
`uxStrength` и т.д., которые недавно подключены к движку матчинга).

## Краевые случаи

- **Повторная обработка при разрешении (разная стоимость).** Эндпоинт на
  повторном запросе всегда прогоняет пайплайн заново, но цена разная:
  - `needs-direction`: 409 срабатывает **до** анализа портфолио, поэтому
    повтор = повторный скрейп + парсинг (анализ при первой попытке не
    запускался).
  - `duplicate`: 409 срабатывает **после** скрейпинга, классификации и анализа
    портфолио, поэтому «Создать всё равно» (`forceCreate`) = повторный
    **скрейп + полный анализ** заново (дороже).
  Осознанный компромисс ради переиспользования готового эндпоинта; для пачки
  5–20 приемлемо.
- **Портфолио без скриншотов → тихий `product` без анализа.** Если скрейпинг
  не дал скриншотов, классификация направления не запускается, направление
  молча становится `product`, анализ портфолио не выполняется, и кандидат
  создаётся со статусом «создан» и пустыми оценками (`visualStrength` и т.д. =
  null). Важно: статус строки **«создан» не гарантирует, что анализ портфолио
  прошёл**. В UI такие строки помечаем подписью «портфолио не
  проанализировано» (определяем по отсутствию оценок в ответе), чтобы рекрутер
  видел разницу и при необходимости перезапустил анализ позже.
- **Дубль-ссылка внутри пачки** → отсеивается на вводе (`parsePortfolioLinks`).
- **Уход со страницы во время обработки** → предупреждение через
  `beforeunload`. Известное ограничение: при навигации внутри SPA (роутинг
  Next.js без полной перезагрузки) `beforeunload` не сработает — для MVP
  приемлемо.
- **AI-квота / ошибка скрейпинга** → строка получает статус «ошибка» с кнопкой
  «Повторить»; остальная очередь не падает.

## Точки входа

- Ссылка «Загрузить пачкой» на странице одиночной загрузки
  (`/candidates/upload`).
- Быстрое действие на главной (`/`).

## Тестирование

- **Юнит-тест** на `parsePortfolioLinks` (дедуп / валидация / нормализация /
  отсев пустых). Явно покрыть нормализацию trailing-slash и регистра, чтобы
  дубли внутри пачки отсеивались надёжно.
- **Ручная проверка** на 2–3 реальных ссылках с запуском приложения: успешное
  создание, попадание в очередь по направлению, попадание в очередь по
  дубликату, ошибка скрейпинга + повтор. E2E-харнесса в проекте нет.

## Что НЕ входит (YAGNI)

- Фоновая очередь и персистентный job-state (вариант B) — не нужно для 5–20.
- Серверный стриминг/SSE (вариант C).
- Массовый импорт сотен/тысяч из архива — отдельный проект при необходимости.
- Загрузка резюме-файлов пачкой — текущий сценарий только про портфолио-ссылки.
- Параллельная обработка (конкурентность > 1) — последовательность безопаснее
  для Playwright и AI-квоты.
